title: "[개인 프로젝트] Kafka 기반 실시간 Twitter 로그 데이터 분석 및 모니터링"
role: "Personal Data Engineering Project"
year: 2022
teamSize: 1
outcomeSummary: "Docker로 Kafka 클러스터(3 broker, ISR 복제)를 직접 구축해 Twitter API 로그를 실시간 수집·ELK 스택으로 분석하고, Burrow·Telegraf·Grafana로 Kafka Consumer Lag까지 실시간 모니터링하는 파이프라인을 구축한 개인 학습 프로젝트입니다."
overview: "로컬 환경에서 Docker로 Kafka 클러스터를 구성하고, Consumer에서 ELK 스택(Logstash, Elasticsearch, Kibana) 컨테이너로 데이터를 전송·처리하는 구조로 Twitter API 로그 데이터를 실시간 처리했습니다. 더 나아가 Kafka Consumer Lag을 모니터링하기 위해 Burrow를 구성하고, Burrow 데이터를 Telegraf를 통해 Elasticsearch에 적재해 Grafana로 시각화한 대시보드를 구성했습니다."
problem: "이전에 구축했던 온·습도 센서 데이터 파이프라인에서는 Kinesis Data Stream의 Producer·Consumer가 늘어나 파이프라인 복잡도가 증가함에 따라 서비스 사용 비용이 함께 증가하는 문제가 있었습니다. 이 문제의 해결책으로 직접 Kafka를 구축·운영하거나 AWS MSK(관리형)를 사용하는 두 가지를 정리했었는데, 이번에는 그중 자체 Kafka를 로컬 환경에 직접 구축해 실시간 로그 데이터 처리와 Consumer Lag 모니터링까지 검증해보고자 했습니다."
constraints:
  - "여러 broker로 구성된 Kafka 클러스터의 고가용성(HA)을 직접 검증해야 함"
  - "유입 데이터에 비해 Consumer 소비가 느려지는 Lag을 실시간으로 감지·시각화해야 함"
  - "로컬 Docker 환경에서 Kafka, Zookeeper, ELK, Burrow, Grafana 등 다중 컨테이너 간 네트워크·환경변수 설정을 직접 해결해야 함"
  - "Twitter API 인증정보 등 민감정보를 소스코드와 분리해 관리해야 함"
approach: "(1) Kafka 클러스터 구성. Docker로 Zookeeper 3대(ZK1~3)와 Kafka broker 3대(Kafka1:9091~Kafka3:9093)를 구성했습니다. Twitter 토픽은 partition 1, replication 3으로 설정해, 3개 broker에 leader 1·follower 2로 데이터를 복제하는 ISR(In-Sync-Replica) 구조를 만들었습니다. (2) 실시간 수집 및 처리. Python(kafka-python, tweepy)으로 작성한 Producer가 Twitter API 로그 데이터를 Kafka로 전송하고, Consumer가 이를 소비해 ELK 스택(Logstash → Elasticsearch → Kibana) 컨테이너로 전달하는 구조로 구성했습니다. (3) Consumer Lag 모니터링. Burrow로 Kafka Consumer의 offset과 broker HEAD offset을 비교해 Lag 상태를 계산하고, Telegraf로 이 데이터를 주기적으로 Elasticsearch에 적재한 뒤 Grafana 대시보드로 시계열 시각화했습니다. (4) 컨테이너 네트워킹 이슈 해결. Docker로 다중 broker를 구성할 때 `KAFKA_ADVERTISED_HOST_NAME`(및 `KAFKA_ADVERTISED_LISTENERS`)을 localhost나 127.0.0.1로 지정하면 멀티 브로커 환경이 제대로 동작하지 않는 문제를 겪었습니다. 현재 할당된 실제 IP로 값을 지정해 해결했습니다."
keyDecisions:
  - decision: "자체 Kafka 클러스터 직접 구축 (AWS MSK 대신)"
    reasoning: "이전 프로젝트에서 Kinesis 사용 시 Producer·Consumer가 늘어날수록 서비스 비용이 증가하는 문제를 겪었습니다. MSK도 결국 오픈소스 Kafka 기반 서비스라 직접 운영하며 내부 동작 방식을 이해하는 게 반드시 필요하다고 판단했고, 향후 서비스가 확장됨에 따라 비용 절감을 위해 온프레미스 환경에 Kafka를 직접 구축·운영할 가능성도 있다고 보고 직접 구축했습니다."
    alternatives:
      - "AWS MSK (Fully Managed Apache Kafka)"
  - decision: "Partition 1 / Replication 3으로 ISR 구성"
    reasoning: "총 3개 broker에 1개 파티션을 leader 1, follower 2로 복제해, 하나의 broker에 장애가 생기더라도 다른 broker에 복제된 데이터로 즉시 복구할 수 있는 고가용성을 확보했습니다."
    alternatives:
      - "단일 broker 또는 무복제(replication 1) 구성"
  - decision: "Consumer를 1개로 구성"
    reasoning: "Kafka로부터 넘겨받은 데이터가 ELK 스택 한 곳에서만 처리되면 됐기 때문에 Consumer는 1개로 충분하다고 판단했습니다. Kafka는 Consumer가 데이터를 읽어도 retention 기간까지 원본이 유지되는 특성이 있어, 필요 시 새로운 Consumer Group을 추가하면 언제든 처음부터 다시 소비할 수 있는 유연성도 함께 확인했습니다."
    alternatives:
      - "여러 Consumer Group으로 병렬 소비 구성"
  - decision: "Consumer Lag 모니터링 도구로 Burrow + Telegraf + Grafana 채택"
    reasoning: "유입 데이터에 비해 Consumer 소비가 느려지면(Lag 값 증가) 장애로 이어질 수 있어 이를 실시간으로 감지할 체계가 필요했습니다. Burrow로 Kafka 자체의 Consumer offset·Lag 상태를 계산하고, Telegraf로 이 데이터를 Elasticsearch에 주기적으로 적재해 Grafana로 시계열 대시보드를 구성하는 방식을 택했습니다."
    alternatives:
      - "Kafka 자체 JMX 메트릭만으로 모니터링"

learnings:
  - "이론으로만 알고 있던 Kafka의 고가용성 구조(ISR, replication)를 직접 클러스터로 구축하며 체감했고, 데이터 양과 retention 기간을 고려해 replication 옵션을 신중히 관리해야 한다는 것을 배웠습니다."
  - "Producer의 `acks` 옵션을 기본값(1)으로 두었는데, 안정성이 더 중요한 상황에서는 속도는 느리지만 신뢰성이 높은 `acks=-1`과 `min.insync.replicas` 설정을 함께 고려해야 한다는 것을 인지했습니다."
  - "Docker 다중 broker 환경에서 `KAFKA_ADVERTISED_HOST_NAME`을 localhost로 두면 안 된다는 것을 직접 겪고 해결하며, 컨테이너 네트워킹에 대한 이해를 다졌습니다."
  - "향후에는 Consumer를 두 그룹으로 나눠, 하나는 분석·시각화(ES/Kibana)를, 다른 하나는 Hadoop HDFS로 데이터를 백업하는 용도로 구성해보는 확장 계획을 세웠습니다."
